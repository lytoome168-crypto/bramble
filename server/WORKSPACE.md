# Workspace backend and digest setup

All `workspace` tRPC procedures require a real authenticated user; cron identities cannot use them. All authenticated users share boards, people and logs, but the inbox is personal. The seeded and generated people are assignment records, not fabricated login accounts (`userId: null`). The seed is transactionally marked complete and never reapplied over edits.

- `workspace.get` query: returns `WorkspaceData` from `shared/work.ts` with all boards, people and logs, and only notifications for people linked to the authenticated user; an unlinked user receives no notifications. `automation.scheduleStatus` is `not_configured` until the shared heartbeat has been registered and `active` after its last successful setup. This is registration state, not live health monitoring.
- `workspace.saveBoard({board})`: validates and returns the saved `Board`; strips values for removed custom columns. Under the row lock it checks the board revision and rejects stale snapshots rather than silently overwriting concurrent edits. Transitions of existing items into `done` notify their assigned person if completion notifications are enabled. Unassigned items have no recipient.
- `workspace.createBoard({name})`: returns a new `Board`.
- `workspace.createAI({prompt})`: calls `gpt-6-luna`, strictly validates 10–20 tasks, 2–5 groups, 3–7 distinct named people with roles, valid indexes and dates no earlier than the current Singapore date, and atomically stores the board and new people. Errors are reported; no fabricated fallback is returned.
- `workspace.createPerson({name,role})`: returns a new `Person`.
- `workspace.linkPerson({personId})`: claims an unclaimed person for the authenticated account and returns the updated `Person`. Repeating a claim is safe; switching to another unclaimed person unlinks all previous people for that account in the same transaction. Missing person returns `NOT_FOUND`, already claimed by another account returns `CONFLICT`, and a failed claim leaves previous links unchanged. The account and target person are row-locked; all writers of `Person.userId` must use this protocol. This is an open self-claim model: authentication alone does not verify a user's real-world identity or entitlement to an unclaimed person. Claiming a person exposes that person's historical notices; switching gives up access to the old person's inbox.
- `workspace.runDigest({boardId})`: returns `{boardId,date,kind:'manual',delivered,skipped,message}`. Manual runs work even when a board's automatic digest toggle is off. They deliver at most once per board/person/Singapore date; retrying that day is safe. Scheduled and manual deliveries have separate keys, so one of each may be delivered on the same date. If new overdue recipients appear later, a subsequent run can deliver to those recipients, but a person already delivered that day is not re-sent updated contents. One success log is retained per board/date/kind, plus individual failure logs.
- `workspace.markRead({id})`: marks only the linked person's notice and returns `{success:true}` (also if already read). Missing and unauthorized notices both return `NOT_FOUND`. Read state belongs to the notice/person and is preserved if the person is later linked to another account.
- Additional `workspace.ensureSchedule({published:true})`: explicit post-publication owner-only registration, returning `{taskUid,status:'active',cron,timezone}`. It requires `OWNER_OPEN_ID` to match the authenticated owner's openId; if this optional environment value is unavailable, use the owner-environment command below instead.

## After publication, register the scheduler

The scheduler targets only the published application. **Do not manually register before the published version contains `/api/scheduled/digest`.** On the first authenticated workspace request in the production application, when a board has the daily digest enabled and registration is missing, the app attempts to register the shared scheduler. Registration errors leave `not_configured` visible in the UI and are retried at most every five minutes on subsequent requests. It is never registered from the development Preview. After publication, an authenticated owner with `OWNER_OPEN_ID` set may also call `workspace.ensureSchedule({published:true})`, or an owner may run in the project sandbox with injected database and Manus service credentials:

```sh
pnpm exec tsx server/setupDigestSchedule.ts --published
```

This creates or reconciles one owner-scoped shared job with cron `0 0 0 * * *` (00:00 UTC = 08:00 Asia/Singapore daily) and persists its returned task UID. Registration can fail for service, publication, permission, or plan-quota reasons; an error is not success. The callback verifies the HS256 scheduler JWT, required expiry, project and cron claims; resolves the token with `GetUserInfoWithJwt`; and looks up the workspace exclusively by returned task UID, ignoring callback-body identifiers. It processes only boards with `digestEnabled` and only assigned, unfinished items whose due date is before Singapore today. Each scheduled board/person/date delivery has a database-enforced unique key, inserted transactionally with the inbox notice; successful retries do not duplicate deliveries. Use the platform's schedule dashboard/logs to check actual executions. If an operator deletes or pauses the job externally, the stored `active` status can become stale; rerun setup after publication to reconcile.
